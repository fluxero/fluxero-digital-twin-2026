# Fluxero Digital Twin
**Predictive control software for Small Modular Hydrogen Plants — from a 10W lab bench to a multi-megawatt commercial site.**

---

## What This Does

The Digital Twin simulates the real-time electrochemical, thermal, and financial behaviour of a PEM electrolyzer stack being fed by erratic renewable power. This is the core problem: standard electrolyzers are designed for flat grid power. Feed them volatile wind or solar DC and the stack undergoes thermal and pressure stress, degrading rapidly. This software models that behaviour and is the foundation for controlling against it.

The same codebase handles a physical lab bench (programmable PSU, single anode/cathode cell) and a commercial site (multi-megawatt wind or solar array) — only the configuration asset changes.

## What Was Built

### Physics Engine — `FluxeroSimulationEngine.cs`
Runs on a fixed 100ms internal timestep independent of Unity's framerate.

- **Hydrogen production** via Faraday's Law: `n(H₂) = (I × η_F × N_cells) / (2F)`
- **Faradaic efficiency** modelled as a Gaussian peak around nominal current density (~95% at rated conditions, dropping off at extremes)
- **Thermal model**: heat balance per timestep — heat generated by overpotential minus heat dissipated to ambient
- **Degradation**: health index 1.0 → 0.0 over stack lifetime, accelerating 3× during thermal stress events
- **Volatile power**: Perlin noise + sinusoidal gusts scaled by `volatilityFactor` (0.0 = flat PSU, 0.8 = gusty wind)

### Configuration — `FluxeroSiteProfile.cs`
ScriptableObject. Create one asset per site via right-click → Fluxero → Site Profile. The engine reads from whichever asset is assigned — no code changes needed to switch between a 10W bench and a 5MW wind farm.

Current assets:
- `Lab_MVP_Bench.asset` — 10W PSU, 1 cell, 25cm², zero volatility
- `Lincoln_Wind_5MW.asset` — 5MW nameplate, 500 cells, gusty wind profile

### Environment Simulator — `FluxeroEnvironmentSimulator.cs`
Drives `nominalPowerKW` and `volatilityFactor` on the active profile in real time using physics-based models:
- **Wind**: IEC standard cubic power curve (cut-in 3 m/s, rated 12 m/s, cut-out 25 m/s)
- **Solar**: irradiance × panel area × efficiency, with cloud-shadow events via Perlin noise
- **Hybrid**: combined wind + solar profile

Presets: Lab PSU / Wind Calm / Wind Moderate / Wind Gusty / Wind Storm / Solar Clear / Solar Cloudy / Solar Dynamic / Hybrid

### Dashboard — `FluxeroDashboardV2.cs` + `InputConfigPanel.cs`
Event-driven — subscribes to engine events, never polls in `Update()`.

- Live gauges: input power, H₂ rate, stack temperature, faradaic efficiency
- Stack health bar (green → amber → red as membrane degrades)
- Scrolling power input graph (line renderer, no third-party library)
- Multi-timeframe yield forecast: 1hr / Today / Week / Month / 3 Months / Year / 5 Years
- System alerts panel with severity colour coding
- Lab mode (V × I sliders) vs Commercial mode (environment dropdown + capacity slider)
- Start / Stop / Reset session controls

### Stack Health Monitor — `StackHealthMonitor.cs`
Records thermal stress events, predicts remaining membrane life in years, surfaces maintenance recommendations to the dashboard.

### Yield Predictor — `FluxeroYieldPredictor.cs`
Projects H₂ yield and revenue across all timeframes from the current instantaneous production rate, applying the degradation model for multi-year forecasts. Deducts OPEX for long-term projections.

### Azure Data Bridge — `FluxeroDataBridge.cs`
REST API stub targeting Azure IoT Hub. Inactive by default. Toggle `useRemoteData = true` and supply a SAS token to activate telemetry push.

### UI Builder — `Editor/FluxeroDashboardBuilder.cs`
Run via **Fluxero → Build Dashboard UI**. Auto-generates the full Canvas hierarchy with correct layout groups, colours, and named GameObjects ready for Inspector wiring.

## Setup

1. Open in **Unity 2022.3 LTS**
2. Open scene `VirtualBench`
3. Select `[FLUXERO_MANAGER]` — confirm a `FluxeroSiteProfile` asset is assigned
4. **Fluxero → Build Dashboard UI** to generate the Canvas
5. Wire Inspector references on `FluxeroDashboardV2` and `InputConfigPanel`
6. Play → **START**

## What to Do Next

### Immediate — finish the UI wiring
The dashboard is built but the Inspector slots on `FluxeroDashboardV2` and `InputConfigPanel` still need GameObjects dragged into them manually. The named objects in the Hierarchy (e.g. `PowerValueText`, `HealthSlider`, `GraphContainer`) map directly to the public fields. Do this before anything else — it makes the software actually usable.

### Connect a real PSU
Add serial port reading to `FluxeroDataBridge.cs` using `System.IO.Ports`. Most lab PSUs (Rigol, Korad, BK Precision) support SCPI commands over USB. This turns the simulation into a real digital twin — the physical voltage and current replace the Perlin noise model, and the predicted H₂ yield can be compared against a gas flow meter in real time.

### Validate the thermal model against hardware
Attach a thermocouple to the physical cell. Log real temperature alongside the predicted `stackTempC`. If they diverge, adjust `thermalMassJperK` and `thermalResistanceKperW` in the site profile until they match. Once calibrated the degradation model becomes physically meaningful.

### Add a second site profile
Create a new ScriptableObject for a real or planned commercial site — different cell count, area, nameplate capacity, wind volatility. Swap it into the engine in the Inspector and confirm all gauges and forecasts rescale correctly. This proves the multi-site architecture works end to end.

### Activate Azure telemetry
In `FluxeroDataBridge.cs`, set `useRemoteData = true`, fill in your IoT Hub hostname and device ID, generate a SAS token from the Azure portal. The state will push as JSON every 5 seconds. This is the foundation for remote monitoring across multiple deployed sites.

### Build the predictive control loop
The current engine reacts — it simulates what is happening. The next step is to make it predictive: ingest a weather API forecast, run the simulation forward 2 hours, and output recommended operating parameter adjustments before volatile conditions arrive. This is what separates the software from a monitoring tool and makes it genuinely defensible.
